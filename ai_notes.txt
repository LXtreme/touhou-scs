TOUHOU SCS: WORKING MANUAL FOR FUTURE CODEX SESSIONS
Updated 2026-10-22 from the current working tree.

PURPOSE AND STATUS
This is Touhou: Shattered Crystal Shards, a Touhou-style bullet hell game built inside Geometry Dash. Python generates the many precisely timed GD triggers needed for bullet patterns, enemies, collisions, damage, and item drops. The playable game also depends on objects and manually authored logic inside touhou scs.gdlvl; the Python files alone are not the whole game. Treat this file as an orientation manual for future development, not a claim that the six-stage game is finished.

The current implementation uses Python >=3.13 and gmdbuilder >=0.2.0. README.md still describes G.js/WSLiveEditor; that is historical context, whereas main.py now loads a .gdlvl file and save_all exports through gmdbuilder. Live-editor export remains supported. triggers.json and quicktesting.js are legacy/experimental artifacts, not the current main.py output path. Package metadata says 0.1.0 while __init__.py says 2.0.0; do not infer release maturity from these inconsistent versions.

CURRENT ENTRY POINT AND DATA FLOW
1. main.py loads Level.from_file("touhou scs.gdlvl") and immediately calls utils.init_level(level). This must happen before importing lib/component/misc because their module-level definitions allocate groups and construct components. Import lib before component when bootstrapping around the circular dependency. init_level is a one-time binding per process.
2. Components register themselves globally during construction. They describe local trigger timelines; building Python objects does not simulate gameplay.
3. Main is caller group 36 and starts Stage.stage1. main.py creates position pointers, reusable bullet behavior templates, and six yinyang patrol enemies. Only stage1 is instantiated; stage2 through stage6 are commented out in lib.py.
4. Each patrol enters from (-60,420) to (90,300) in 1.5 seconds, sweeps to (270,300) in 3 seconds, then exits to (420,420) in 1.5 seconds. It schedules eight 24-bullet radial waves with randomized timing, alternating bullet1 and bullet3 pools between enemies. Enemies enter 1.8 seconds apart beginning at stage time 1, have 10 HP, and drop 5-13 score items plus 10-15 power items. Randomness occurs during generation, so separate builds can differ.
5. BulletAlloc.start() enables deferred pattern allocation. spawn_enemy records attack start times. After constructing the stage and collision infrastructure, BulletAlloc.resolve() sorts deferred requests by local time + stage offset and assigns pooled bullets in actual firing order. This reduces premature reuse caused by constructing entire enemy timelines sequentially. It is not a runtime free-list or lifetime-aware allocator. Timed.Line currently allocates directly rather than deferring.
6. main.py calls add_enemy_collisions, add_disable_all_prefabs, add_plr_collisions, and add_pickup_collisions once, resolves allocation, then save_all(level=level, live_editor=False). Running it writes the level file; it is not a read-only check.

STRUCTURE AND CORE ABSTRACTIONS
- touhou_scs/component.py: Component and fluent trigger-building API; contexts; validation; pointer-circle setup; Multitarget; deferred BulletAlloc; instant/timed pattern helpers.
- touhou_scs/lib.py: registries, Spell, Stage, concrete bullet/enemy pools, pointer pool, guider geometry, enemy HP/death/drop wiring, export layout and validation/statistics.
- touhou_scs/misc.py: shared gameplay collision generation and despawn/damage templates. Detailed map below.
- touhou_scs/movements.py: Bezier registration, numerical fitting, GD movement generation, optional animated previews.
- touhou_scs/enums.py: GD easing values, reserved groups, game groups, placeholder IDs, item/collision constants. Item aliases gmdbuilder.enum.Item.
- touhou_scs/utils.py: bound group allocator unknown_g, calltracker, remap parsing/building, timing/rounding helpers, placeholder validation.
- touhou_scs/types.py: protocols and object/trigger-area typing for cross-module APIs.
- touhou scs.gdlvl: actual level and permanent prefabs/runtime logic. Keep group contracts synchronized with code.
- test_triggers.py: pytest coverage of trigger properties/validation, contexts, patterns, spawn limits, solid groups and Bezier behavior. conftest.py binds a fake allocator and imports lib first; fake_level avoids file/editor export. test.py is an executable live-editor scratchpad, not the unit-test suite. pdh.py is currently only a guarded level-loading/bootstrap skeleton.
- prefab_prep.py: executable live-editor utility which duplicates an embedded prefab string, remaps groups/parent groups/collision IDs/link IDs, honors a blacklist, offsets copies horizontally, removes copied color-index metadata, and exports. It operates on editor state when run.
- rearrange_pickups.py: one-off level migration from P301-330/B331-340/score341-450 to P301-370/B371-380/score381-490. It shifts B/score by 40 and clones power prefabs. It writes permanent objects, removing the generated-object tag from clones. Do not rerun as routine build setup; it assumes the old layout.
- setup_curves.py: registers common movement curves at ultra quality, forcing recomputation; registration rewrites the curve registry in movements.py. Restart afterward to refresh CurveType.
- pyproject.toml: setuptools package, strict basedpyright configuration, Ruff exceptions, pytest options. Only gmdbuilder is declared as a runtime dependency; numerical/preview imports in movements.py may require additional installed packages.

WHAT A COMPONENT IS AND HOW TO USE IT
Component(name, callerGroup, editorLayer=4) owns a trigger list and a caller group. Calling that GD group runs the generated trigger sequence. It automatically joins lib.all_components. Most builder methods return self, allowing chains. Each method's time argument is local execution time; t usually means the duration of that particular animation. Time becomes editor X placement during export; it is not a Python sleep. enum.TICK is 1/240 second.

set_context(target=..., groups=..., include_caller=...) selects the target object group and trigger execution groups for subsequent methods. The target is what a trigger affects; the execution groups determine when/how it is called. These are different roles. clear_context resets state; temp_context restores prior state on leaving a with block. include_caller=False is essential for conditional branch triggers that must execute only through their branch groups. Mark physical object targets with enforce_solid_groups through the provided helpers; export rejects accidental use of component/trigger groups as solid objects, with pool exemptions.

The API includes Spawn with remaps/delay/reset behavior, Toggle, MoveTowards, MoveBy, GotoGroup, SetPosition, Rotate, PointToGroup, Follow, Alpha, Pulse, Scale, Stop/Pause/Resume, Collision, Count, Pickup/PickupModify, Timer/TimerStart/TimerStop/TimerOp, plus TriggerFromObj/TriggerFromStr escape hatches. Scale shares generated keyframe components through a ScaleSettings cache. rgb converts a base-red prefab's color to HSB adjustments, rather than assigning arbitrary base colors.

assert_spawn_order(True/False) records ordering requirements for layout/export. Treat it as a deliberate correctness setting. Ordered actions and reset-remap behavior interact with GD's spawn-chain limit; lib._enforce_spawn_limit analyzes trigger execution/call chains. Do not solve failures by casually disabling validation.

Reusable templates use placeholder group IDs: EMPTY_BULLET=10, EMPTY_TARGET_GROUP=20, EMPTY1=21, EMPTY2=23, EMPTY_EMITTER=24, EMPTY_COLLISION=104. Spawn remaps specialize them for an actual bullet, enemy, target pointer, emitter, or callback. EMPTY_MULTITARGET=25 is reserved for the fan-out machinery. Check each pattern's required/excluded placeholders before adding behaviors.

Multitarget builds shared binary fan-out components for 1,2,4,8,16,32,64 calls, combining them to support 1-127 targets per request. Its callback remaps five placeholder channels into each target's resources. Existing callers split larger workloads into 64-sized batches until the remainder is <=127. Components containing Spawn triggers warn about spawn-limit risk when used as Multitarget templates.

POOLS, GEOMETRY, AND PATTERNS
BulletPool.next() cycles an inclusive range and returns (bullet group, collision group), where collision group = bullet group + pool size. It reserves both ranges from unknown_g. Reuse is cyclic; enough pool capacity and sensible timing still matter.
Enemy bullets: bullet1 501-1000 (500, oriented), bullet2 1501-2200 (700, oriented), bullet3 2901-3600 (700), bullet4 4301-4700 (400). Pickups use the same pool abstraction: power301-370 (70), bombs371-380 (10), score381-490 (110). Player shots: regular ofuda6300-6339 (40), homing6230-6299 (70), bomb balls6200-6229 (30), needles6380-6431 (52). The registered_bullet_pools registry therefore contains more than hostile bullets.

circle1 is the prebuilt 1080-direction guider circle: center/all6181, directional groups5101-6180, giving 1/3-degree aim resolution. Lazy GuiderCircles allocate only the directional pointers actually requested. lib.pointer cycles through 250 generated pointers, records shared memberships, and exports objects once. This is a finite reused resource, not unlimited allocation.

component.pointer.SetPointerCircle(time, location=..., follow=...) snapshots circle1 geometry around an emitter, with preparation at time-4 ticks, -3 ticks, and -2 ticks. follow=True allocates a common transform group for the used pointers and center; movement/follow still needs appropriate triggers, as main.py demonstrates. CleanPointerCircle finalizes required pointer-copy triggers and shared memberships, then clears the builder's active circle. It is construction-time finalization, not a runtime delete. Must call before export; avoid exhausting/reusing pointers while previous behavior needs them.

instant.Arc uses selected angular pointers to specialize a reusable bullet template. instant.Radial wraps Arc for a full closed circle without duplicating the endpoint. instant.Line emits simultaneous bullets with different travel durations to form a speed-separated line. timed.RadialWave schedules repeated radials; timed.Line emits a sequence with time gaps. timed.BezierMove applies a registered relative curve with dx/dy/duration to the active target.

EnemyPool supports multiple groups per enemy slot. yinyang6340-6379 uses two groups per slot (20 enemies). next() returns the complete tuple. spawn_enemy initializes HP in the main group's timer two ticks before attack, enables the enemy one tick before, starts the attack through a per-slot off-switch, and starts in-level HP-check loop150. Its remaps connect enemy ID, despawn behavior, off-switch, and drop component. Death fades/scales/pulses the enemy, stops its attack, plays SFX, disables it after0.3 seconds, and starts drops. Current _new_drop_comp creates a fresh component and pickup allocations for each call; a docstring claims identical-config reuse, but there is no such cache in the implementation. Drops are staggered across PICKUP_SPAWN_TIME=0.2 seconds, snap to the enemy position, toggle on, then invoke in-level random-movement group129 remapped per pickup.

Bezier movement fits curves to combinations of GD easing/move triggers. Gentle curves use arc-length resampling and basis fitting; more complex curves use the older piecewise polynomial optimizer. Registration persists CurveType/CURVE_PARAMS by rewriting movements.py. Runtime applies multiple MoveBy terms; optional matplotlib/GIF previews visualize the fit. Numerical fitting and preview generation are tooling, not an in-game Python runtime.

MISC.PY: GAMEPLAY CONTRACTS AND IMPLEMENTATION
Collision roles: hitbox is the weapon, hurtbox is the target. IDs: boundary1, player hurtbox2, player graze3, bomb4, shared enemy hitbox5. Pickup collection uses player outer/screen-boundary hitbox6. Global collision startup is group17; graze callback34, player hurt35, hostile-bullet despawn27. These refer to existing level logic as well as generated components.

add_disable_all_prefabs(): one-time generator for group32. A shared Toggle(False) template remaps EMPTY_BULLET to every slot of all BulletPools and every main enemy slot; Multitarget batches reduce duplicate templates. This includes pickups and player shots because of the common registry. Enemy secondary groups are not independently enumerated.

add_plr_collisions(): base component18 installs four persistent hostile-bullet interactions: leaving boundary disables the bullet; touching graze calls34; bomb contact calls27; player contact activates that bullet's own group, whose wrapper invokes hurt35 with the bullet remap. Every hostile bullet gets a derived collision group used to gate its player-hit wrapper, allowing spawn grace periods. Startup wrappers belong to17. It explicitly enumerates bullet1-4 rather than the registry, since pickups/player shots must not receive hostile-bullet behavior. A TODO asks for separate registries. Shared enemy hitbox5 also triggers hurt35 and graze34; a source warning notes this path uses placeholders without per-enemy remaps.

add_enemy_collisions(): handles player shots hitting enemies, not enemies hitting the player. It enumerates the main group of each registered enemy slot and all shots in PLAYER_SHOT_TYPES. Each shot gets a permanent boundary-exit collision via a SEPARATE base component. This separation is essential: mixing boundary onExit with enemy-hit setup caused load-time onExit to disable the bullet group and permanently kill enemy-hit collision handling. For each enemy and shot type, Multitarget specializes a common collision template to bullet ID, enemy ID, and that shot type's damage/despawn component. Collision count scales with enemies times shots even though templates are shared. Homing tracker collision14 against each enemy invokes a wrapper which disables tracker block133 and appends a raw advanced-follow edit trigger targeting136/20 for retargeting. Keep those raw level contracts intact when changing homing.

add_pickup_collisions(): wires bottom-border exit despawn, collection, pickup animation/SFX, power progression, and magnet movement. Each pool's startup wrapper in17 remaps pickup10 and handler21. A shared intermediate Spawn preserves the remapped handler call. Collection tests against player outer hitbox6, not tiny hurtbox2; bottom boundary is enum.BOTTOM_BORDER=12. For every pickup, triggers in group124 dynamically GotoGroup(player2, t=0.5, easing1/rate2). This generates the magnet action; the condition that activates124 lives elsewhere.

Power pickups add0.05 to timer12, capped at4.00. A comparison tree distinguishes already max, reaching max, crossing an integer level, and ordinary increments. Comparisons use0.001 tolerance/epsilon to absorb floating-point accumulation. Below max, pickup awards100 score; integer crossings additionally play a power-up SFX. Reaching max snaps power to4, calls Full Power for100 score and a distinct SFX; full-power visuals remain TODO. Already-max pickups give200 score (the actual fixed amount; the nearby comment suggesting power*200 is stale). Power animation scales2x, fades/pulses white for0.3 seconds, resets alpha, then disables the pickup. Bomb pickups use similar animation and increment bomb item11 at0.3 seconds. Score pickups add100 to item16 at0.3 seconds. All three have a common pickup SFX.

Shared despawn1 animates enemy bullets: shrink0.25, fade/black pulse over1 second, reset alpha and disable at1 second. despawn2 animates player bullets: shrink/fade with blue pulse and disable at0.2 seconds. enemy_bullet_despawn is callback27 and delegates to despawn1; it is not itself the damage calculation.

make_shot_despawn(name, damage[5], despawn_g) builds conditional damage branches for power-level groups143-147. The active power group selects a negative TimerOp ADD to the enemy's HP timer (EMPTY_TARGET_GROUP), then blue enemy hit feedback, SFX, and a despawn callback execute. Correct level toggling of those power groups is an external runtime dependency. Regular damage:0.4/0.5/0.6/0.7/0.8. Homing:0.3/0.35/0.4/0.5/0.6. Bomb:1/1.2/1.4/1.6/2, with EMPTY_BULLET as callback rather than despawn2. Needles use literal expressions0.7*1.15,0.8*1.15,0.9/2*1.15,1/2*1.15,1.2/2*1.15; preserve intentional balance/firing-rate assumptions rather than normalizing the nonmonotonic values.

PLAYER_SHOT_TYPES pairs the four concrete pools with their damage/despawn components. To add a shot type: define its prefab/pool in lib.py, create damage/despawn behavior, register the pair here, and implement the corresponding in-level firing behavior. The registry automatically includes it in enemy-hit and boundary generation. Pool registration alone does not create a complete firing system.

add_* functions use calltracker and reject duplicate calls. calltracker marks a function called even if it raises, via finally; a failed partial build is best retried in a fresh process. Module-level component registries, pointer export, and init_level similarly make one fresh process per build the practical workflow.

EXPORT, CHECKS, AND WORKING HABITS
save_all checks spawn limits, validates solid targets, exports pointer mappings once, rejects unfinished pointer circles/reserved9999/missing object IDs, spreads triggers into the configured area (1350,1300)-(20000,4500), preserves required execution order with spacing checks, prints statistics/budget analysis, appends generated objects, then exports to file or editor. Its docstring still mentions JSON/main.js, but its actual implementation writes through gmdbuilder. Default object-budget reporting is200,000; older design notes target250,000. Groups have a hard9999 ceiling.

Use venv/Scripts/python.exe -m pytest test_triggers.py for the focused unit suite when changing relevant logic. Use Ruff/basedpyright as appropriate. Do not use test.py, main.py, prefab_prep.py, or the migration as harmless smoke tests: they can write files or editor state. Python tests verify generated data/validation, not actual GD timing, visuals, or live-editor stability. Validate those in GD.

When adding a trigger/object wrapper, inspect EVERY relevant GD default; prior KeyframeAnim defaults caused bugs. Collision delays/onExit can be engine/editor state problems: original advice is reload/recompile, allow live-editor export to finish before alt-tabbing, or pan to trigger area first. Retain modular spell construction so stage practice can run each spell in isolation. Allocate new groups through unknown_g and review existing level contracts rather than inventing hardcoded IDs.

IMMEDIATE DIRECTION AND ROADMAP INTERPRETATION
The active code is a stage1 patrol/drops test and now has working generation for enemy HP/death, power/bomb/score pickups, homing collision hooks, and four player shot pools. Build on and validate these systems before assuming the old TODOs mean they must be implemented from scratch. Basic bombing has bomb pools/damage hooks but this code alone does not establish complete keybind/texture/gameplay integration. Power pickup visuals at full power are explicitly unfinished.

The original backlog below remains the user's source of planned additions; it is not an ordered commitment. Near-term items include finishing bombing, new ring variants (followed formations, radial spawn offsets, stacked speeds), tighter pointer setup, and optimizations to follow/follow-rotate selection and shared keyframes. Separate hostile-bullet/pickup/player-shot registries would make collision generation safer. Placeholder-based complete enemy attacks remain constrained by GD spawn limits. Broader UI, title screen, backgrounds, keybind editor, additional bullet types, lasers and SFX remain design work unless confirmed in the level. Three character movement profiles were noted as set but not final. The shard buff/deathbomb gimmick and six-stage story are design intent; the inspected Python does not implement that complete progression.
